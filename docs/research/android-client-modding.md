# Research: can 3dmigoto-family mods reach an emulator-hosted Android client?

**Ticket:** [#85](https://github.com/Derek-X-Wang/gmm/issues/85), child of [#81](https://github.com/Derek-X-Wang/gmm/issues/81) (Wayfinder: automate Star Rail dailies).
**Question:** Is any 3dmigoto-family modding possible against an emulator-hosted Android Star Rail client, or is the Android side permanently separate from GMM's mod half?
**Scope:** Feasibility verdict only. Not v1. Not a design. Decides whether the idea ever returns as a separate effort.

## Verdict: **No — with one narrow, unproven exception that is not the same technique**

Standard 3dmigoto-style D3D11 resource-hash modding, as GMM/XXMI implement it today, **cannot reach an Android client running inside a consumer emulator (MuMu Player, LDPlayer, BlueStacks) on Honkai: Star Rail or any HoYoverse title.** Three independent parts of the chain break, any one of which is fatal on its own:

1. Even in the best case — an emulator whose host-side rendering genuinely streams individual Android draw calls into a real Direct3D 11 context on Windows (a real, documented architecture pattern; see §4) — 3dmigoto's resource identification is a **runtime CRC32C hash of the actual GPU resource bytes plus descriptor metadata** (§1), and Android/mobile builds use **different platform-mandated texture compression formats** than the PC build (§5). The hashes would not match even with perfect hook visibility. This alone kills the idea for the "same asset, same hash" workflow GMM's Model Importers are built around.
2. Whether that best-case host-side D3D11 context even exists for MuMu/LDPlayer/BlueStacks specifically is **unverifiable** — all three are closed-source with no public rendering-architecture documentation beyond a marketing-level "renderer: OpenGL / DirectX / Vulkan" toggle (§3). We cannot confirm from primary sources that the "DirectX" option produces per-draw-call visibility rather than a single composited blit of the guest framebuffer.
3. Even granting (1) and (2), the D3D11 traffic a hook would see belongs to **the emulator's own host rendering process** (its `.exe`, compositing potentially several guest windows/instances), not a process that behaves like a native Windows game — a structurally different and unresolved injection target from every other GMM-supported title (§4).

The one thing that *is* real and *does* mod Unity/IL2CPP games running natively on Android is a completely different technique family — native code injection + IL2CPP method hooking on-device — and it has **no known application to any HoYoverse title** and **no resemblance to GMM's D3D11-resource-swap model** (§6). It's evidence that "modding a mobile Unity client" is possible in general, not evidence that GMM's approach extends there.

**This is a flat no for GMM's actual technique.** The one-paragraph separate-effort sketch below exists only because the ticket asks for it if the answer isn't a *flat* no in the broadest sense (some Android-side modding of some HoYoverse-adjacent game, by some technique, is imaginable) — not because the narrow exception is a live option for GMM.

## 1. How 3dmigoto / `3dmloader.dll` actually attaches

GMM's own docs already establish the mechanics precisely (`docs/architecture/loader.md`, `docs/adr/0001-gplv3-and-embed-3dmloader.md`, `CONTEXT.md` → Loader): `3dmloader.dll` (from [`SpectrumQT/XXMI-Libs-Package`](https://github.com/SpectrumQT/XXMI-Libs-Package), GPLv3, forked from [`bo3b/3Dmigoto`](https://github.com/bo3b/3Dmigoto)) installs a Win32 **CBT hook** (`SetWindowsHookEx`-family) that watches window creation across *all* processes, and `LoadLibraryW`'s a target DLL into whichever process creates a window — see `src-tauri/crates/loader/src/windows.rs`'s doc comments, which reproduce the entry-point signatures from XXMI Launcher's `dll_injector.py`. That injected DLL is the Model Importer's `d3d11.dll` proxy, which is itself a **DirectX 11 modding wrapper** — the 3Dmigoto repository describes itself as such, and ships build artifacts literally named `d3d11.dll` / `nvapi64.dll` so it loads in place of the real system libraries via DLL search-order hijacking ([bo3b/3Dmigoto](https://github.com/bo3b/3Dmigoto)). `XXMI-Libs-Package`'s own README describes the project as "a fork of 3dmigoto, a Direct3D modding tool" with DirectX11/DirectXGI components ([SpectrumQT/XXMI-Libs-Package](https://github.com/SpectrumQT/XXMI-Libs-Package)).

Once loaded, the proxy DLL wraps the real `ID3D11Device` — `DirectX11/HackerDevice.cpp` opens with the comment *"Wrapper for the ID3D11Device. This gives us access to every D3D11 call for a device, and override the pieces needed"*, and implements `HackerDevice::CreateBuffer`/`CreateTexture2D`, which compute a hash and then delegate to the real device pointer ([bo3b/3Dmigoto — `HackerDevice.cpp`](https://github.com/bo3b/3Dmigoto/blob/master/DirectX11/HackerDevice.cpp)). Individual GPU resources are matched by a hash computed **from the resource's runtime byte content and descriptor**, using a hardware CRC32C routine — confirmed directly in source: `3Dmigoto/DirectX11/ResourceHash.cpp`'s `CalcTexture2DDescHash()` hashes the (resolution-normalized) `D3D11_TEXTURE2D_DESC`, and `CalcTexture2DDataHash()` hashes the actual pixel payload via `crc32c_hw()` ([bo3b/3Dmigoto — `ResourceHash.cpp`](https://github.com/bo3b/3Dmigoto/blob/master/DirectX11/ResourceHash.cpp)). `TextureOverride`/`ResourceOverride` INI sections key on exactly this hash (e.g. `hash = 428c56cd`). The XXMI fork used for Star Rail specifically is [`SilentNightSound/SR-Model-Importer`](https://github.com/SilentNightSound/SR-Model-Importer) ("a version of 3DMigoto/GIMI that has been modified to be compatible with Star Rail"), packaged for XXMI Launcher as [`SpectrumQT/SRMI-Package`](https://github.com/SpectrumQT/SRMI-Package) — both target the **PC** client only.

**What has to be true for this to apply at all:** the target process must (a) be a real Windows process that creates a window 3dmloader's CBT hook can observe, and (b) call the genuine Win32 D3D11 API with individual `CreateBuffer`/`CreateTexture2D` calls per game asset that the hook can intercept — not merely present a single finished frame to the OS.

## 2. What graphics path Android game clients use

HoYoverse titles including Star Rail are Unity-engine games. On Android, the platform itself has moved to **Vulkan as the primary low-level graphics API**, with OpenGL ES retained for compatibility but no longer under active feature development — Android's own developer documentation states this directly and adds that "current versions of the Unity and Unreal game engines choose Vulkan as their default renderer on compatible Android devices" ([developer.android.com — Vulkan overview](https://developer.android.com/games/develop/vulkan/overview)). Unity's manual confirms the same: Android supports Vulkan and OpenGL ES only, with Vulkan enabled by default on new Android projects ([docs.unity3d.com — Graphics APIs](https://docs.unity3d.com/Manual/GraphicsAPIs.html)), and Unity's `GraphicsDeviceType` enum lists Direct3D 11/12 only under Windows targets, never Android ([docs.unity3d.com — `GraphicsDeviceType`](https://docs.unity3d.com/ScriptReference/Rendering.GraphicsDeviceType.html)). Direct3D is a Windows-only API with no Android implementation. This is why part (b) in §1 is not automatically satisfied on Android: the game itself never calls D3D11, on-device or off. Anything that shows up as D3D11 on a Windows host must come from a translation layer added by the emulator, not from the game.

## 3. What MuMu Player / LDPlayer / BlueStacks do to translate that graphics path on the host

All three run the Android guest inside a VM/hypervisor on the Windows host (BlueStacks documents Hyper-V-based operation explicitly — [BlueStacks: Hyper-V-enabled Android Pie instances](https://www.bluestacks.com/blog/bluestacks-exclusives/bluestacks-hyper-v-enabled-en.html); [BlueStacks 5 Hyper-V system requirements](https://support.bluestacks.com/hc/en-us/articles/4415238471053-System-requirements-for-BlueStacks-5-on-Hyper-V-enabled-Windows-10-and-11)). LDPlayer's own product documentation exposes a user-facing renderer choice between **OpenGL and DirectX** in its Advanced settings ([ldplayer.net — graphics/FPS setup guide](https://www.ldplayer.net/blog/play-games-at-higher-frame-rate-on-ldplayer.html)), and MuMu Player's own marketing pages describe "DirectX rendering and OpenGL acceleration" plus a Vulkan-based "Turbo/Nebula" renderer for Unity/UE4 titles ([mumuplayer.com](https://www.mumuplayer.com/)). BlueStacks 5's own support docs describe an "Engine" setting offering OpenGL, DirectX, and (on newer Android images) Vulkan ([BlueStacks Support — graphics renderer article](https://support.bluestacks.com/hc/en-us/articles/360059893151-How-to-use-a-graphics-renderer-on-BlueStacks-5); page returned HTTP 403 to automated fetch at review time, content confirmed via search-result cache rather than a direct re-fetch — flagged as **secondary-confirmed** pending re-verification).

**None of the three publishes a technical architecture document.** MuMu Player's only public GitHub organization contains a single `.github` profile repo with no technical content ([github.com/MuMu-Player-12](https://github.com/MuMu-Player-12)). No BlueStacks or LDPlayer engineering blog describing internal rendering pipeline mechanics was found. This is a **hard verification ceiling**: we cannot confirm from primary sources whether their "DirectX" render option streams individual guest draw calls into a real per-resource D3D11 context, or simply blits a single composited Android framebuffer into a D3D11 swapchain for display. Both are plausible engineering choices; only the former would give a 3dmigoto-style hook anything meaningful to see.

What we *can* confirm is the shape such a translation layer would take if it does expose real resources, because architecturally equivalent, fully open, and fully documented cases exist: Google's own reference Android virtualization stack (Cuttlefish/gfxstream) and the Android Studio Emulator, both detailed next.

## 4. Would a translated D3D11 surface expose real game resources, or only a composited frame?

This is answerable in the general case, and the answer is genuinely "it depends on the translation architecture" — not a flat no. Three real, documented technologies bound the possibility space:

- Google's own **Cuttlefish** (AOSP's reference Android virtual device) docs describe exactly two GPU-acceleration modes, and both preserve individual-call granularity rather than shipping a composited frame: in **gfxstream** mode, "OpenGL and Vulkan API calls are forwarded directly to the host"; in **virgl** mode, "OpenGL API calls are translated into an intermediate representation... communicated to the host and the virglrenderer library on the host translates the intermediate representation back to OpenGL API calls" ([source.android.com — Cuttlefish GPU acceleration](https://source.android.com/docs/devices/cuttlefish/gpu)). gfxstream itself is described as "a code generator that makes it easier to serialize and forward graphics API calls from one place to another: from a virtual machine guest to host" ([android.googlesource.com/.../gfxstream](https://android.googlesource.com/platform/hardware/google/gfxstream/)).
- **ANGLE** ("Almost Native Graphics Layer Engine"), Chromium's translation layer, sits on the host side of such a pipe on Windows and **translates OpenGL ES calls to Direct3D 9 or Direct3D 11** ([chromium.googlesource.com/angle — README](https://chromium.googlesource.com/angle/angle/+/main/README.md)). Android Studio's own emulator release notes confirm this pairing directly, including an explicit `-gpu d3d11` mode and an auto-migration from the deprecated D3D9 ANGLE backend to D3D11 ([developer.android.com — Emulator release notes](https://developer.android.com/studio/releases/emulator)); the official android-emulator-dev mailing list separately describes ANGLE's purpose on Windows as translating "GLES2 calls directly into DirectX ones" ([groups.google.com/g/android-emulator-dev](https://groups.google.com/g/android-emulator-dev/c/9o8OZezxq9c)).
- As the requested "translation layer that is comparably well documented" analog on the D3D-to-Vulkan side: **DXVK** self-describes as "a Vulkan-based translation layer for Direct3D 8/9/10/11" and exposes a runtime HUD with per-frame `drawcalls`, `pipelines`, and `descriptors` counters — direct evidence that a serious translation layer operates, and can be observed, at individual-draw-call granularity, not as a single blit ([github.com/doitsujin/dxvk](https://github.com/doitsujin/dxvk)).

Chained together (gfxstream/virgl → ANGLE's D3D11 backend), this **is** an architecture where each individual guest draw call and texture upload becomes a real, individually-hooked `ID3D11Device` call on the Windows host — not a single composited blit. This is the one place in this investigation where "narrow yes, architecturally" is honest: **if** a consumer emulator's DirectX renderer option is built the same way (per-call streaming + a D3D11-backed translator), a 3dmigoto-style hook attached to the right process would see individual `CreateTexture2D`/`CreateBuffer`/`Draw` calls corresponding to real game assets, not a single frame. Whether MuMu/LDPlayer/BlueStacks are built this way is exactly the thing §3 could not confirm — Google's own reference stack is not evidence about their internals, only evidence that the pattern is real and buildable.

There is also a further, independent snag even in that best case: the D3D11 traffic would belong to **the emulator's own rendering/compositor process** — its `.exe` (e.g. a `MuMuPlayer.exe`/`HD-Player.exe`/`dnplayer.exe`-family process), which may composite multiple guest windows, other emulator UI chrome, and possibly multiple running instances into shared device/swapchain state — not a process that behaves like a native Windows game with one process per game session, the assumption every other GMM-supported title satisfies. Whether that process statically or dynamically links D3D11 (a precondition for 3dmigoto's DLL-search-order/LoadLibrary-based interception to find anything to wrap), and whether per-app resource streams are even distinguishable inside it, is unanswered by any source found here.

Even granting the best case on both fronts, §1 and §5 are independently fatal to actually matching anything.

## 5. Do Android clients ship the same assets, keyed by the same hash, as PC?

No — and this is confirmed independent of any emulator-internals uncertainty. 3dmigoto's hash is a **CRC32C of the resource's raw bytes at hook time** (§1, `ResourceHash.cpp`). Unity's own documentation is explicit that texture compression is chosen **per build platform**: for Windows/desktop standalone builds, Unity's recommended formats are **BC7** (RGBA, higher quality) or **DXT5**, and **DXT1** for RGB; for Android, the recommended formats are **ASTC** (preferred on modern GPUs) or **ETC2** as a fallback — a completely different, platform-specific compressed representation of the same logical texture ([docs.unity3d.com — Choose a GPU texture format by platform](https://docs.unity3d.com/6000.0/Documentation/Manual/texture-choose-format-by-platform.html)). Android App Bundles go further and ship **multiple ASTC/ETC2/DXT variants split by device capability**, chosen at install time ([developer.android.com — Target texture compression formats in Android App Bundles](https://developer.android.com/guide/playcore/asset-delivery/texture-compression)).

Because the compressed byte layout differs by platform and target format, the same logical character texture produces a **different CRC32C hash** on Android than on PC, even disregarding any mesh/LOD or vertex-layout differences mobile builds commonly carry for performance. A PC-authored `TextureOverride` hash from an existing GameBanana SRMI mod has no reason to ever match an Android-client resource, even in the best-case injection scenario from §4.

## 6. Existing real community efforts modding these games — on Android, by any technique

**No community effort was found that mods a HoYoverse title on Android, or on an emulator-hosted Android client, by any technique.** Search results for "Genshin Impact Android mod" / "Star Rail Android mod" surfaced only: (a) PC-side mod-asset repositories (e.g. `GI_Assets`-style texture/model dumps) and PC-client mod managers such as [`SilvVF/HoyoModManagerGo`](https://github.com/SilvVF/HoyoModManagerGo), all consumed by PC tools like GMM/XXMI with no Android-side application, and (b) low-credibility "cheat APK" repositories with anti-cheat-bypass and currency-generation claims that could not be verified and read as spam/malware rather than genuine engineering effort — not cited here as evidence of anything real.

What *is* real, verifiable, and directly relevant is the general **Android IL2CPP-game modding ecosystem**, which every actual project found belongs to — and it is a completely different technique family from GMM's GPU-resource interception:

- **Native inline-hooking against `libil2cpp.so`/JNI**: [`LemonLoader/MelonLoader`](https://github.com/LemonLoader/MelonLoader), an Android port of the PC MelonLoader Unity mod loader, depends on **Dobby** (a native inline/PLT hooking library) and JNI bindings — i.e. it hooks compiled game logic in the native library, not GPU calls. [`ByNameModding/BNM-Android`](https://github.com/ByNameModding/BNM-Android) documents the same standard stack explicitly: IL2CPP class/method/field introspection paired with a native hooking backend (Dobby, ShadowHook, or Substrate).
- **Frida-based dynamic instrumentation**: tooling such as [`AeonLucid/frida-il2cpp`](https://github.com/AeonLucid/frida-il2cpp) attaches Frida's JS-driven native hooking to `libil2cpp.so` at runtime to read/patch game logic — process injection, but into IL2CPP method calls, not `ID3D11Device` resource creation.
- **Xposed**, the general-purpose Android hooking substrate, works by replacing `/system/bin/app_process` so it can hook methods in any Zygote-forked app at the ART/Dalvik level ([Xposed API docs](https://api.xposed.info/reference/de/robv/android/xposed/XposedHelpers.html)) — a managed-method hook, again unrelated to the GPU/rendering pipeline.
- The Meta Quest Beat Saber modding stack (Quest headsets run a forked Android) is a mature, full end-to-end example of the same family: APK patching to load a native modloader ([`sc2ad/scotland2`](https://github.com/sc2ad/scotland2)) that hooks `il2cpp_init` and lets mods call into game logic via a C++ hooking library ([`zoller27osu/beatsaber-hook`](https://github.com/zoller27osu/beatsaber-hook)), orchestrated by a GUI patcher ([`Lauriethefish/QuestPatcher`](https://github.com/Lauriethefish/QuestPatcher)).

Every one of these operates at the **IL2CPP/native-library or Java/ART method-hooking layer** — reading and patching compiled C# game logic — or, separately, as **static AssetBundle extraction/repack tooling** (e.g. [`Escartem/AnimeStudio`](https://github.com/Escartem/AnimeStudio), an actively maintained AssetStudio fork that explicitly supports "all 4 major Hoyo games" for offline asset extraction, not live injection). None of it intercepts a GPU API to swap resources by content hash. This is consistent with §§2–4: there is no Windows D3D11 surface on the Android side for a 3dmigoto-style tool to attach to in the first place, so the entire live Android-modding ecosystem organized around a different attachment point instead. It resembles GMM's *mod-manager UX* (a patcher tool, installable mods) far more than it resembles GMM's *technique*.

## Separate-effort size sketch (only because the ticket asks for it if not a flat no)

If this were ever revisited, the only technically coherent path resembles the general Android IL2CPP-hooking ecosystem in §6 (Dobby/Substrate-style native hooking + IL2CPP introspection, à la LemonLoader-Android/BNM-Android/Frida-il2cpp, or the Quest QuestLoader/Scotland2/beatsaber-hook pipeline as a mature full example) — **not** the D3D11-hash-swap model GMM is built around. It would require: reverse-engineering Star Rail's Android IL2CPP binary to find stable class/method offsets across game updates (a treadmill separate from GMM's current INI-based hash mods, with no shared tooling); a native Android modloader and patched-APK distribution pipeline (APK signing, install-time patching, likely incompatible with the Play Store / official-client update flow and closer to jailbreak-style sideloading); a from-scratch hook/injection library for the emulator's guest environment (nothing in `src-tauri/crates/loader` transfers, since 3dmloader's CBT-hook + LoadLibraryW model is Win32-specific and has no Android equivalent); and a completely separate asset pipeline, since GameBanana's existing GIMI/SRMI/ZZMI/WWMI/HIMI/EFMI mod library (PC textures/meshes, PC hashes) would not be reusable for whatever Android-side format an IL2CPP hook could actually swap. This is effectively a second product sharing nothing with GMM's current loader, Library, or Mod model except the target game — which is why the recommendation is to close this thread, not size it further.
