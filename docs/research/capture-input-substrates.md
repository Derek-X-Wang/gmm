# Substrate survey: capturing pixels and injecting input into a Windows HSR client

Research for issue #83.

## TL;DR

**Recommend the PC client directly — Windows Graphics Capture for pixels, `SendInput` for taps/keys — as the v1 substrate.** This should be stated as the headline finding rather than a footnote, since the ticket explicitly asked not to assume it: on balance, none of the six Android-emulator substrates in this ticket beat driving the native Windows client, once the *cumulative* cost of the emulator path is weighed against its *one* genuine advantage.

The case for the PC client is several independently sufficient reasons stacking, not one silver bullet:
- **Zero new detection primitive.** `src-tauri/src/core/detect/star_rail.rs` already finds, validates, and caches this exact install. Every emulator substrate would need a *new kind* of detector GMM doesn't have today — an ADB liveness probe against a port that, for MuMu and (per community reports) BlueStacks, is not fixed and not guaranteed stable across restarts (§ table, §4, §6).
- **GMM already owns the process.** Per `CONTEXT.md`'s "Game Session" concept, GMM spawns the Star Rail process itself and holds the 3dmigoto loader in-process for the session's lifetime — so GMM already has a handle to the exact running process this feature would target, before any `FindWindow`-style lookup is even needed. No emulator substrate offers anything like this; each one is a separate, GMM-uninvolved process tree.
- **No new third-party EULA/redistribution surface.** It's the game the user already owns, launched through the client GMM already detects. By contrast this research could not confirm a consumer automation-permitting EULA clause for any of the three consumer emulators, and found genuinely discouraging signals for two of the three (BlueStacks' ToS boilerplate reads plausibly hostile to always-on automation; LDPlayer/MuMu's precise terms could not be retrieved at all — §4–6, §Confidence).
- **Better raw capture fidelity and performance.** Windows Graphics Capture is a native, GPU-backed, push-frame API with no ADB/scrcpy hop in the middle (§10), versus an ADB-mediated screencap or scrcpy stream layered on top of the emulator's own virtualization overhead.
- **A secondary, narrower point:** since this lives inside a mod manager, keeping automation on the same client GMM already manages avoids the operational awkwardness of running a second, parallel Android instance of the same HoYoverse account purely to script dailies — a different device fingerprint, a second login, and (for any UI element affected by an installed mod's re-skin) potentially different on-screen geometry than what the user actually sees day to day. This is a real but secondary consideration, not a categorical disqualifier: daily-task automation mostly reads UI chrome (dialogs, buttons, resource counters), which is unaffected by 3dmigoto's model/texture reskins, so an emulator's pixels would not literally be "unusable" for this specific feature the way they would be for, say, visually verifying a mod's appearance.

Against all of that, the emulator path has exactly one substantive technical edge, and it is the exact axis the ticket flagged as the deciding one: ADB-injected input (`input tap`, or scrcpy's control protocol) lands inside the Android guest's own input subsystem and is **not** gated by Windows window focus, so it structurally survives the emulator window being minimized or unfocused — while Win32 `SendInput` is, by Microsoft's own API design, injected into the single systemwide focused input queue and cannot target a specific unfocused/minimized window ([SendInput docs](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [Keyboard Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input)). That is the real "attended v1 / unattended later" tension the ticket asked about. It is real, unresolved by this research, and is the single strongest argument an emulator advocate has — but it is outweighed for v1 by the accumulated PC-client advantages above, and it is not unique to emulators as a *solution*: the standard fix (a virtual HID / kernel-mode input driver, e.g. an Interception-style filter driver) can deliver focus-independent input to the native PC client too, without switching substrate at all. See the Confidence and Open Questions section for why this is flagged as the next research item rather than resolved here.

## Per-substrate detail

### 1. ADB over TCP/IP and AVD port ranges (primary: developer.android.com)

Android's own `adb` docs describe two connection modes: Android 11+ devices pair wirelessly via `adb pair ipaddr:port` (mDNS/TLS-based, dynamic port), while Android 10 and earlier require an initial USB connection, `adb tcpip 5555` to switch the daemon to network mode, then `adb connect device_ip:5555` — port 5555 is the conventional default but is just a TCP port chosen by the `adb tcpip` invocation, not a protocol constant ([developer.android.com/tools/adb](https://developer.android.com/tools/adb)). All `adb` clients talk to the local `adb` server on TCP port `5037` regardless of target. For the AVD emulator specifically, each running instance claims a *pair* of sequential ports — an even console port and the next odd adb port (instance 1: console `5554`, adb `5555`; instance 2: console `5556`, adb `5557`; …), and the adb server auto-discovers emulators by scanning odd ports `5555`–`5585`, i.e. up to the first 16 concurrent instances ([developer.android.com/tools/adb](https://developer.android.com/tools/adb); confirmed for the single-instance case via [developer.android.com/studio/run/emulator-networking-interconnect](https://developer.android.com/studio/run/emulator-networking-interconnect), which documents `telnet localhost 5554` as the console port for "the first emulator instance launched"). This is the cleanest, most deterministic ADB story of anything surveyed.

### 2. scrcpy (primary: github.com/Genymobile/scrcpy)

scrcpy requires `adb` and (for anything other than USB-OTG mode) USB/network debugging enabled on the target — its own FAQ states "`scrcpy` execute[s] `adb` commands to initialize the connection with the device" and "if `adb` fails, then scrcpy will not work" ([scrcpy FAQ](https://github.com/Genymobile/scrcpy/blob/master/FAQ.md)). The README advertises 30–120 fps depending on device and 35–70 ms end-to-end latency, with an option to trade latency for jitter-smoothing buffering ([scrcpy README](https://github.com/Genymobile/scrcpy)). Input is not a `minitouch`-style raw socket protocol; scrcpy ships its own client/server control protocol (`doc/control.md`) where the desktop client sends structured control messages and the on-device `scrcpy-server` (pushed and run via `adb push` + `app_process`) injects them as Android `AMOTION_EVENT`/key events through the platform's own input-injection path, including a documented "virtual finger" technique for simulating pinch/secondary touches from a single mouse cursor ([scrcpy control.md](https://github.com/Genymobile/scrcpy/blob/master/doc/control.md)). This is materially more capable and more actively maintained than the openSTF-era tools below.

### 3. minitouch / minicap (primary: github.com/openstf)

Both openSTF repositories carry an explicit, identical archive banner fetched directly from GitHub: *"This project along with other ones in OpenSTF organisation is provided as is for community, without active development,"* directing users to the **DeviceFarmer** fork, which is described as where "active development has been moved" ([openstf/minicap](https://github.com/openstf/minicap), [openstf/minitouch](https://github.com/openstf/minitouch) — minitouch's README additionally states "This repository was superseded by https://github.com/DeviceFarmer/minitouch"). DeviceFarmer's forks exist and see occasional issue activity, but secondary community commentary describes them as effectively stuck at old Android versions and not comparable to scrcpy's actively-maintained protocol (lower confidence — [dev.to writeup, secondary source](https://dev.to/omnarayan/openstf-is-dead-the-best-alternative-for-mobile-device-labs-in-2025-2j5o)). **Conclusion: minitouch/minicap are legacy and superseded by scrcpy's own protocol for any new work; do not build on them.**

### 4. MuMu Player (NetEase)

Official docs confirm `adb connect 127.0.0.1:7555` as the documented connection command, with troubleshooting guidance to `adb kill-server` and retry if the device doesn't appear ([mumuplayer.com/help/win/connect-adb.html](https://www.mumuplayer.com/help/win/connect-adb.html)). The same page notes newer multi-instance builds may default the main instance to port `16384` instead, and directs users to an in-app "Device Diagnostic" menu to find the live port — i.e. **the port is not a fixed constant GMM could hardcode**; it must be discovered at runtime. NetEase publishes its own walkthrough for playing Star Rail on MuMu Player, claiming performance "up to 240 FPS" ([mumuplayer.com/blog/play-honkai-star-rail-on-pc.html](https://www.mumuplayer.com/blog/play-honkai-star-rail-on-pc.html)) — this is vendor marketing, not an independent benchmark or a HoYoverse endorsement. A full consumer EULA with explicit automation/redistribution language could not be located; only a "Developer Platform User Agreement" was found, which governs a different developer-facing surface ([mumuplayer.com/developer-platform-user-agreement.html](https://www.mumuplayer.com/developer-platform-user-agreement.html)) and is not evidence either way about ADB-driven automation of the desktop app itself.

### 5. LDPlayer

LDPlayer's own EULA (`ldplayer.net/other/protocol.html`) and Terms of Service (`ldplayer.net/other/terms-of-use.html`) both returned HTTP 403 to automated fetch in this research pass, so their exact text on automation/redistribution could not be verified from the primary source directly — this is marked **unresolved / lower confidence** rather than settled. Search-engine synthesis (not a page LDPlayer itself served to this research) describes a per-instance ADB port scheme consistent with the standard AVD pattern (instance 0 → console `5554`/adb `5555`, instance 1 → `5556`/`5557`, …) and a documented multi-instance command-line tool (`dnconsole.exe adb --index N --command ...`). LDPlayer ships first-party keyboard-mapping and multi-instance/macro tooling clearly aimed at the same "run several accounts unattended" audience as BlueStacks and MuMu. No official HoYoverse endorsement found; community sources describe a January 2026 LDPlayer update specifically addressing HSR memory/rendering issues, but this was not confirmed against an LDPlayer-hosted changelog in this pass.

### 6. BlueStacks

BlueStacks has an official, named support article for enabling ADB (Settings → Advanced → "Android Debug Bridge" toggle) ([support.bluestacks.com/hc/en-us/articles/23925869130381](https://support.bluestacks.com/hc/en-us/articles/23925869130381-How-to-enable-Android-Debug-Bridge-on-BlueStacks-5) — page content itself returned 403 to automated fetch; title/existence and toggle location confirmed via search-engine snippet of that same official page, so treat the exact wording as lower confidence even though the article's existence is not in doubt). Community sources consistently describe BlueStacks 5 as **randomizing its ADB port on every startup**, requiring the user to re-check Settings → Advanced → Developer Options each session — this directly answers the ticket's "is it stable across restarts?" question in the negative, though it is community-sourced rather than confirmed from BlueStacks' own article text. BlueStacks' Terms and Privacy policy, fetched directly, prohibits reverse engineering, scraping ("crawls, scrapes, or spiders any page, data, or portion of... the Services"), and "processes that run or are activated while you are not logged into the Services" ([bluestacks.com/terms-and-privacy.html](https://www.bluestacks.com/terms-and-privacy.html)) — this reads like boilerplate written for BlueStacks' own cloud/account services rather than a targeted anti-automation clause for the local desktop app, and is muddied by BlueStacks itself officially shipping a "Macros" feature and heavily marketing "Multi-Instance" + "Eco Mode" for exactly the kind of unattended multi-account gacha grinding this ticket is circling ([bluestacks.com/features/multi-instance.html](https://www.bluestacks.com/features/multi-instance.html); [Eco Mode support article](https://support.bluestacks.com/hc/en-us/articles/360052834772-How-to-run-multiple-instances-of-BlueStacks-5-more-efficiently-using-Eco-mode)). Net effect: BlueStacks is the *most explicit* of the three consumer emulators about supporting background/unattended multi-instance operation as a first-party feature, but has the murkiest automation-specific ToS language of the three.

### 7. Google Play Games on PC

Google's own developer documentation is unambiguous that this is a **curated, opt-in catalog**, not a general-purpose Android emulator: a title must be specifically built/optimized for PC and published through Google's PC-compatibility program to appear at all ([developer.android.com/games/playgames/pc-compatibility](https://developer.android.com/games/playgames/pc-compatibility), [overview](https://developer.android.com/games/playgames/overview)). ADB access is documented only for Google's separate **developer**-facing "Play Games Developer Emulator," a distinct downloadable tool aimed at testing PC builds pre-launch ([developer.android.com/games/playgames/pg-emulator](https://developer.android.com/games/playgames/pg-emulator)) — the consumer end-user app that ships to players has no documented ADB surface. Contrary to the ticket's prompt to check for a discontinuation announcement: **no evidence of discontinuation was found**; the opposite is true — Google's own 2025 GDC post describes the product graduating from beta to general availability and expanding its PC game catalog ([blog.google/products-and-platforms/platforms/google-play/google-play-android-gdc-2025](https://blog.google/products-and-platforms/platforms/google-play/google-play-android-gdc-2025/)). Whether HoYoverse has opted Honkai: Star Rail into the PC catalog specifically could not be confirmed from a primary Google or HoYoverse source in this pass — treat as **unresolved**, though it is moot for GMM regardless (no ADB surface either way).

### 8. WSA (Windows Subsystem for Android)

**Confirmed dead**, with an exact date from Microsoft's own docs, now archived: *"Starting March 5, 2025, Windows Subsystem for Android™ and the Amazon Appstore are no longer available in the Microsoft Store"* ([learn.microsoft.com/en-us/windows/android/wsa](https://learn.microsoft.com/en-us/windows/android/wsa/) — the page itself is marked `is_archived: true`, `ROBOTS: NOINDEX,NOFOLLOW`, canonicalized to a `previous-versions` URL, i.e. Microsoft has formally retired the doc, not just added a deprecation notice). The original announcement was posted by a Microsoft account (`andreww-msft`) on the official `microsoft/WSA` GitHub repo on March 5, 2024, giving one year's notice ([github.com/microsoft/WSA/discussions/536](https://github.com/microsoft/WSA/discussions/536)). Independent of the shutdown, the same archived docs describe a VM lifecycle actively hostile to unattended automation even while WSA was alive: apps are paused after 3 minutes without activity ("Lightweight Doze") and the whole VM stops after 7 minutes, both triggered by the app window being minimized. The same docs also note, under "Security": *"There are no plans to add detection for cheats/macro/bot/suspicious behaviors detection in the short-term,"* which — had WSA survived — would have been a mild positive signal for automation tolerance, now moot. **WSA is not a viable substrate at all as of the current research date (2026-08-15).**

### 9. AVD (Android Studio emulator)

Best-documented headless story of any substrate: `-no-window` "disables graphical window display on the emulator... useful when running the emulator on servers that have no display. You can access the emulator through `adb` or the console," and `-gpu mode` selects the rendering backend (e.g. software rendering via `swiftshader_indirect` for GPU-less hosts) ([developer.android.com/studio/run/emulator-commandline](https://developer.android.com/studio/run/emulator-commandline)). Despite that operational polish, AVD is very likely the **least able of all seven substrates to run Star Rail at all**: only "Google Play"-tagged system images ship Google Play Services, and Star Rail's own anti-cheat/integrity checks are understood (secondary/community sourced, HoYoverse has published nothing specific found in this research) to lean on Google's Play Integrity API, which is widely reported as flagging AVD-class virtual environments as non-genuine even on Play-tagged images ([Play Integrity API overview, secondary](https://en.wikipedia.org/wiki/Play_Integrity_API)). No HoYoverse-published statement on this was found — **inferred, lower confidence on the mechanism, higher confidence on the outcome** (AVD is a developer testing tool, not a gaming platform, and nothing in Google's or HoYoverse's public docs suggests otherwise).

### 10. Windows Graphics Capture + SendInput (PC client direct)

**Capture.** `Windows.Graphics.Capture` (`GraphicsCaptureItem` + `Direct3D11CaptureFramePool`) is a native, GPU-backed capture API that targets a specific window or the whole display via a system picker, delivering frames through a push-style `FrameArrived` event rather than a polling loop ([learn.microsoft.com screen-capture guide](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)). It can capture an **occluded** window (covered by other windows) without issue and, with user consent via `GraphicsCaptureAccess.RequestAccessAsync(GraphicsCaptureAccessKind.Borderless)`, can even suppress the yellow "this is being captured" border introduced alongside `IsBorderRequired` in Windows 10 version 2104 ([IsBorderRequired docs](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession.isborderrequired)). It **cannot** meaningfully capture a fully **minimized** window — a minimized window has no live composited surface for the Desktop Window Manager to hand off, so capture either stops or serves a stale last-drawn frame; this specific limitation is not spelled out in Microsoft's primary how-to guide (which is silent on minimization) but is corroborated by a Microsoft Q&A community thread and general OBS/game-capture community consensus ([Microsoft Q&A discussion](https://learn.microsoft.com/en-us/answers/questions/5516715/winrt-windows-graphics-capture-leads-to-applicatio); OBS forum discussion) — **treat the "impossible to capture minimized windows" claim as medium confidence**, not a direct quote from Microsoft's reference docs, though the underlying "minimized windows have no live DWM surface" mechanism is a well-established, high-confidence fact about Windows composition generally. `GraphicsCaptureItem.Closed`'s own docs only describe the event firing when the *target is closed* (or seamlessly replaced by another window), with no mention either way of minimization ([GraphicsCaptureItem.Closed docs](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscaptureitem.closed)).

**Input.** `SendInput` "inserts the events... serially into the keyboard or mouse input stream" and explicitly has **no window-handle parameter at all** — there is nothing to target, by design ([SendInput reference](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)). Microsoft's own Keyboard Input Overview spells out where those events actually land: *"The system posts keyboard messages to the message queue of the foreground thread that created the window with the keyboard focus... The window that has the keyboard focus receives... all keyboard messages until the focus changes to a different window"* ([Keyboard Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input)). In other words, `SendInput` always targets whatever currently holds systemwide OS focus — to aim it at Star Rail, Star Rail's window has to be the foreground window at the moment of the call, full stop; there is no way to send it input while another window is focused without first calling `SetForegroundWindow`, which itself steals focus and would visibly interrupt whatever the user is doing on the PC at that moment. `SendInput` is additionally subject to UIPI (User Interface Privilege Isolation) and "fails when blocked by UIPI" with no distinguishing error code (same reference). A separate, lower-level alternative — `PostMessage`/`SendMessage` with `WM_KEYDOWN`/`WM_LBUTTONDOWN` targeted at a specific `HWND` without stealing focus — does exist, but is well known (and lightly corroborated here via community/GameDev.net discussion, not an authoritative Microsoft statement) to be ignored by many real games, because games commonly read input via Raw Input or DirectInput-style device polling rather than the window-message queue that `PostMessage` writes into; Microsoft's own Raw Input docs describe `RIDEV_NOLEGACY` specifically as a way for an app to *stop* receiving the legacy window messages that `PostMessage` relies on, which is suggestive but not dispositive of how Star Rail's own input layer behaves (not directly verified against Star Rail's own binary in this research). **This asymmetry — capture survives occlusion but not minimization, input survives neither occlusion nor loss of focus — is the crux fact the ticket was after, and it is now pinned down against Microsoft's own API documentation rather than inferred.**

**Everything else.** This substrate needs no new install-detection work: GMM's existing `src-tauri/src/core/detect/star_rail.rs` already finds, validates, and caches the exact install this feature would target — registry uninstall-key walk, common-path fallback, exe + `StarRail_Data` Unity-folder validation. Better still, per `CONTEXT.md`'s "Game Session" concept, GMM already *spawns* the Star Rail process itself and holds the 3dmigoto loader in-process for the session's lifetime — so during a Game Session GMM already has a live handle to the exact process this feature would target, which is a stronger starting point than any window-title lookup. The only genuinely new capability needed is locating the *window* handle for capture/input purposes once the process is running (`FindWindow`/`EnumWindows` by class or title, or deriving it from the process GMM already holds), which is a runtime concern orthogonal to install detection. It is also the only substrate that shows GMM's own mod output, since it's the actual DirectX client with 3dmigoto injected, not a separate Android build — worth noting for any future feature that needs to see mod-affected visuals specifically, though daily-task automation's UI-reading needs are largely indifferent to this (see TL;DR).

### 11. HoYoverse / Star Rail anti-automation stance

HoYoverse publishes a "Fair Gaming Declaration" for Star Rail and a HoYoPlay Terms of Service PDF; both exist at stable, official URLs ([hsr.hoyoverse.com/en-us/news/111244](https://hsr.hoyoverse.com/en-us/news/111244); [HoYoPlay ToS PDF](https://fastcdn.hoyoverse.com/static-resource-v2/2024/07/01/1ed4cce564ae5dee2f903d37e814b1e0_6707783454148192051.pdf)), but **neither could be rendered as extractable plain text by this research's automated fetch tooling** — the news page is a client-rendered SPA that served only a loading shell, and the PDF's text layer did not extract cleanly. The commonly cited language — *"The use of plug-ins, accelerators, scripts, or other third-party tools that disrupt the fairness of the game is strictly prohibited"* — comes from a search-engine paraphrase of MiHoYo's declaration, not a direct quote pulled from the fetched primary document in this research pass. **Treat the exact wording as commonly-understood-but-not-independently-verified in this research; the existence and general thrust of an anti-automation policy is not in serious doubt, but the precise legal text was not confirmed first-hand.** This is a pre-existing risk category GMM already operates inside of by injecting 3dmigoto at all (ADR 0001); scripted, unattended input arguably reads closer to "automation tool" than passive visual-mod DLL injection does, and is flagged as an open risk below rather than resolved.

## Does GMM's `src-tauri/src/core/detect/` pattern transfer?

GMM's existing per-game detectors (e.g. `star_rail.rs`) follow one shape: walk `HKLM`/`HKCU` uninstall registry keys for a `DisplayName` match, collect `InstallLocation` values, fall back to a list of common `Program Files`/drive-root paths, and validate each candidate by checking for the game's exe *and* a companion Unity `_Data` directory (`mod.rs`, `star_rail.rs:37-48, 62-84, 107-181`).

- **PC client (existing target):** No change needed — this is exactly the install this feature would use. New work is limited to a runtime `HWND` lookup once the process is running; that's a capture/input-time concern, not a detection-time one.
- **MuMu / LDPlayer / BlueStacks:** All three are conventional Windows installers, so registry-uninstall-key detection is *structurally* plausible the same way it works for HoYoverse's own installer — but this research could not confirm any of the three vendors' exact `DisplayName`/`InstallLocation` registry shape from a primary source, so it would need to be verified empirically against a real install before relying on it. Even once path detection works, it only proves the *emulator* is installed — it says nothing about whether an Android device/instance is currently *running* or which ADB port it bound this session (MuMu's port is explicitly dynamic; BlueStacks' is reported to randomize per restart). A GMM detector for any of these would need a **second, new kind of check GMM doesn't have today**: an ADB liveness probe — `adb devices` after attempting `adb connect` against the vendor's documented/likely port(s), or reading the port out of the emulator's own settings/registry/config file where one exists. This is a materially different detection primitive (network/process probe) than GMM's current filesystem-only heuristic.
- **Google Play Games on PC:** Path/registry detection is plausible (it's a normal signed Windows installer) but detection would dead-end there, since there's no documented ADB surface to confirm liveness or drive input/capture against — the existing detect pattern would tell GMM "the app is installed," never "the game is running and reachable."
- **WSA:** Moot — no longer installable from the Microsoft Store as of March 5, 2025.
- **AVD:** A genuinely different detection primitive: Android SDK / `ANDROID_HOME` discovery and `avdmanager list avd` rather than registry-uninstall-key + exe-validation. Not deeply investigated in this pass (**low confidence / open**), but clearly a bigger lift than adapting the existing pattern, and moot anyway given AVD very likely can't run HSR (see §9).

**Bottom line for this section:** only the PC-client path reuses GMM's existing detection code as-is. Every emulator path would need genuinely new detection logic — an ADB-liveness step (connect-and-probe against a documented or discovered port) layered on top of, or instead of, filesystem detection — and even then would only confirm the emulator app is installed and an instance is reachable, not that it is a good substrate on the other merits (§ Final recommendation).

## Final recommendation

**v1 substrate: the PC client directly — Windows Graphics Capture for pixels, `SendInput` for input.**

**Runner-up: MuMu Player**, as the best-documented and most officially HSR-marketed of the Android emulator options (clean official ADB docs, vendor-published Star Rail walkthrough, more polished than LDPlayer's paywalled-behind-403 docs or BlueStacks' more openly automation-hostile-sounding ToS language).

**The specific, concrete reason the runner-up loses is an accumulation of disadvantages that together outweigh its one real advantage, not a single silver-bullet disqualifier:**
1. **New detection primitive required, and it's shakier than GMM's existing one.** GMM's registry-walk + exe-validation pattern only proves MuMu is *installed*; it says nothing about whether an instance is *running* or which ADB port it bound this session. MuMu's own docs admit the port is not a fixed constant — newer builds may default to `16384` instead of the documented `7555`, requiring the user to check an in-app diagnostic panel ([mumuplayer.com](https://www.mumuplayer.com/help/win/connect-adb.html)). That is a materially less reliable foundation than the exe-plus-`_Data`-folder check GMM already ships.
2. **No confirmed EULA cover for this use.** MuMu's consumer EULA with explicit automation/redistribution language could not be located at all in this research (only a differently-scoped "Developer Platform" agreement was found); LDPlayer's and BlueStacks' equivalent pages either blocked automated fetch or read as plausibly (if ambiguously) hostile to always-on automation (§4–6).
3. **Worse raw capture path.** Any emulator screen-capture route is ADB/scrcpy-mediated, layered on top of the emulator's own virtualization overhead — categorically slower and higher-latency than Windows Graphics Capture's native, GPU-backed, push-frame path against the real client (§10).
4. **Operational duplication.** Automating dailies on MuMu means running a second, parallel Android instance of the same HoYoverse account — a separate login/session and multi-GB install — purely to script menus that the user's own already-installed, already-GMM-detected PC client can drive directly.

**MuMu's one real, substantive advantage — ADB-injected input is not gated by Windows focus, so it structurally works while the window is minimized or unfocused, unlike `SendInput` against the PC client — is real and is exactly the axis the ticket flagged as deciding.** It is not dismissed here; it is the single strongest argument for an emulator. But it does not outweigh points 1–4 for a v1 that is explicitly attended (the PC client's window can simply stay foreground while the user is present, at which point `SendInput` works fine), and it is not unique to emulators as a *solution* — the standard focus-independent-input workaround (a virtual HID / kernel-mode input driver) is applicable to the native PC client too, and is the recommended next research step for the unattended phase rather than a reason to switch substrates now (see Confidence and Open Questions).

**The PC-client path dominates, and this should be read as the headline finding of this research, not a footnote.**

## Confidence and open questions

**Lower-confidence claims (secondary/community-sourced, flagged explicitly above where they occur):**
- BlueStacks' ADB port "randomizes every restart" — community-sourced, not confirmed from BlueStacks' own support article text (which 403'd automated fetch).
- LDPlayer's per-instance ADB port formula and its EULA/ToS automation language — LDPlayer's own pages returned HTTP 403 to automated fetch; relied on search-engine synthesis instead of primary text.
- MuMu Player's and BlueStacks' precise consumer EULA stance on ADB-driven automation specifically (as opposed to general reverse-engineering/scraping prohibitions) — not conclusively located for either vendor.
- Whether Windows Graphics Capture can capture a truly minimized window at all — Microsoft's own how-to guide is silent on this; the "impossible" claim traces to a Microsoft Q&A community thread and general capture-community consensus (OBS forums), not a Microsoft reference-doc statement.
- Whether `PostMessage`-based input (as opposed to `SendInput`) would actually reach Star Rail specifically while unfocused — not tested against the real binary; inferred from how games generally consume Raw Input/DirectInput versus window messages.
- HoYoverse's exact Fair Gaming Declaration / ToS wording on automation — the primary pages exist at stable URLs but did not render as extractable text via automated fetch in this pass; the commonly cited "plug-ins, accelerators, scripts... strictly prohibited" line is a search-engine paraphrase, not a first-hand quote.
- Whether Honkai: Star Rail is actually published into Google Play Games on PC's opt-in catalog — not confirmed from a primary Google or HoYoverse source (moot for GMM either way, since the consumer app has no documented ADB surface).
- AVD's inability to run HSR via Play Integrity — the general mechanism (Play Integrity flags virtual/non-genuine environments) is documented; HoYoverse's specific enforcement against AVD specifically was not found in a primary HoYoverse source, so the outcome is inferred rather than confirmed.

**Open risks worth carrying forward, not resolved by this research:**
- **Anti-cheat/integrity detection of window capture and synthetic input on the PC client itself.** This research did not find a primary HoYoverse source describing what, if anything, Star Rail's client-side anti-cheat does in response to `Windows.Graphics.Capture` usage or `SendInput`-driven automation specifically (as distinct from its general, already-acknowledged prohibition on "plug-ins, accelerators, scripts"). GMM already carries analogous risk via 3dmigoto DLL injection (ADR 0001); whether scripted capture/input meaningfully increases detection risk over and above that baseline is unknown and worth a follow-up.
- **The unattended/unfocused-input gap on the PC-client path is real and unsolved by this research.** `SendInput`'s focus requirement is now pinned to Microsoft's own docs, but this research did not investigate concrete alternatives (e.g. a virtual HID/kernel-mode input driver, or an Interception-style filter driver) that the community commonly uses to route input to a specific process without OS-level focus. That's the natural next research question when GMM actually reaches the "unattended" phase — not "switch to an emulator," since the emulator path is disqualified on mod-compatibility grounds regardless of how its input story compares.
- **Legal/ToS risk of automating the HoYoverse client at all** is acknowledged as commonly understood but was not pinned to first-hand primary text in this pass (see above) — worth a dedicated follow-up fetch (e.g. via a JS-rendering-capable fetch path, or requesting the PDF's text export directly) before GMM ships any unattended automation feature, since the exact scope of "third-party tools" matters legally in a way a paraphrase doesn't resolve.
